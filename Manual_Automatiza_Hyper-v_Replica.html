Automatiza_Hyper-v_Replica.ps1

Implantação e gestão completa do Hyper-V Replica em projetos de campo — da preparação do servidor (domínio ou workgroup, HTTPS com certificado autoassinado) ao failover e ao monitoramento com dashboard.

v1.0 Windows Server 2019+ PowerShell 5.1 Executar como Administrador

01 Visão geral

O Hyper-V Replica é o recurso nativo do Windows Server que mantém uma cópia offline (replica) de cada VM em um segundo host, com envio assíncrono de alterações a cada 30 s, 5 min ou 15 min. Em caso de desastre no servidor primário, a replica é promovida com poucos cliques — sem storage compartilhado e sem licenciamento adicional.

Este script empacota todo o ciclo de vida do recurso em três menus interativos:

[1]

Preparar o servidor

12 etapas com detecção do que já foi feito: papel do servidor, domínio/workgroup, certificado HTTPS, firewall, instalação da função Hyper-V com resume pós-reboot e checklist final de saúde.

[2]

Administrar a replicação

Habilitar replicação por VM, replicação inicial (rede/agendada/mídia externa), failover de teste, planejado e não planejado, suspender/retomar, replicação estendida para um 3º servidor.

[3]

Monitorar e reportar

Visão rápida no console, dashboard HTML com saúde de todas as VMs, últimos eventos de erro do VMMS, exportação CSV e re-execução do checklist.

02 Requisitos

RequisitoDetalhe
Sistema operacional Windows Server 2019 ou superior. O Hyper-V Replica não existe em Windows 10/11 — o script detecta e bloqueia a execução em SO client.
Privilégios PowerShell aberto como Administrador (o script valida na entrada).
Servidores Mínimo 2 hosts (primário + secundário). Opcional: 3º host para replica estendida.
Rede entre os hosts Porta 80/TCP (Kerberos/HTTP) ou 443/TCP (Certificado/HTTPS) liberada entre os servidores, nos dois sentidos.
Identidade Domínio: todos os hosts no mesmo domínio AD (ou domínios confiáveis) → pode usar Kerberos.
Workgroup: autenticação por certificado é obrigatória, e o nome do workgroup deve ser idêntico em todos os servidores.
Armazenamento Pasta local no(s) servidor(es) de destino para receber as replicas (ex.: D:\Replicas), com espaço para os discos das VMs replicadas.
Função Hyper-V Se ausente, o próprio script oferece a instalação (Install-WindowsFeature) — exige uma reinicialização.
⚠ KERBEROS NÃO CRIPTOGRAFA Com Kerberos (HTTP/80) o tráfego de replicação viaja sem criptografia. Se os dados atravessam redes não confiáveis (link entre sites, por exemplo), prefira Certificado (HTTPS/443) mesmo em ambiente de domínio.

03 Fluxo de implantação em campo

A ordem de execução importa: o servidor primário gera o certificado e registra a topologia; os demais servidores importam esse material a partir da própria pasta do script.

No servidor PRIMÁRIO — Menu 1

Execute a preparação completa. Informe o papel Primário, o ambiente (domínio/workgroup) e os FQDN + IP de todos os servidores da topologia. Em HTTPS, o certificado é gerado aqui, com o FQDN de todos os hosts no SAN, e exportado para HyperV_Replica_Cert.pfx na pasta do script.

Copie a PASTA DO SCRIPT para o secundário

Leve a pasta inteira (script + .pfx + .cer) por pendrive ou compartilhamento. Anote a senha do PFX — ela será pedida na importação e nunca é gravada em disco.

No servidor SECUNDÁRIO — Menu 1

Execute a preparação informando o papel Secundário. O script detecta o PFX na pasta, pede a senha, valida o certificado (EKU, SAN, validade) e conclui firewall + servidor replica + autorizações.

(Opcional) Servidor ESTENDIDO — Menu 1

Mesmo processo do secundário, com papel Estendido, para a topologia de 3 níveis: primário → replica → estendido.

De volta ao PRIMÁRIO — Menu 2, opção 1

Habilite a replicação de cada VM (frequência, pontos de recuperação, VSS, compressão) e dispare a replicação inicial.

Valide — Menu 2 opção 4 e Menu 3

Faça um teste de failover no replica (não afeta a produção) e gere o dashboard HTML para registrar a saúde do ambiente na entrega do projeto.

ℹ REEXECUTAR É SEGURO Todas as etapas são idempotentes: o que já está configurado é detectado e exibido como [OK] ... (já configurado — pulando). Se um reboot interromper o processo, basta executar o script novamente — ele continua de onde parou usando o arquivo de estado.

05 Certificado HTTPS (workgroup ou criptografia)

Para HTTPS, cada host precisa de um certificado não expirado, com chave privada, EKU Client + Server Authentication, cadeia terminando em raiz confiável e CN/SAN igual ao FQDN do host. O script atende a tudo isso com ferramentas nativas do Windows:

✖ CERTIFICADO AUTOASSINADO NÃO FUNCIONA O Hyper-V Replica rejeita um certificado que seja a própria raiz (emissor = requerente), com o erro 0x80092007 — "O certificado especificado é autoassinado". Ele exige um certificado que encadeie até uma raiz. Por isso o script gera uma cadeia de dois níveis.

Estratégia: uma CA raiz + um certificado com todos os FQDNs

[CA raiz] CN=Hyper-V Replica Root CA -> LocalMachine\Root (10 anos) | assina [Host] CN=hv01.lab -> LocalMachine\My (5 anos) SAN = hv01.lab, hv02.lab | EKU = Server Auth + Client Auth
  • No primário, o script cria a CA raiz e depois o certificado do host assinado por ela (via New-SelfSignedCertificate -Signer), com o FQDN de todos os hosts da topologia no SAN (RSA 2048, SHA-256).
  • A CA raiz vai para LocalMachine\Root (e é removida de "Pessoal", onde não é o lugar dela); o certificado do host fica em LocalMachine\My.
  • Dois arquivos são gerados na pasta do script: HyperV_Replica_RootCA.cer (CA raiz pública) e HyperV_Replica_Cert.pfx (certificado do host + chave privada, protegido por senha). Os dois precisam ser copiados para os demais servidores.
  • No secundário/estendido, o script instala primeiro a CA raiz (sem ela o certificado não encadeia), depois importa o PFX pedindo a senha (até 3 tentativas), e valida cadeia, EKU, SAN e validade antes de aceitar — se o FQDN local não estiver no SAN, ele orienta a regenerar a cadeia no primário.
  • Em todos os hosts é gravado DisableCertRevocationCheck = 1 em HKLM\...\Virtualization\Replication — obrigatório com CA privada (não há CRL publicada para consultar; KB 2767928).
✖ A SENHA DO PFX NÃO É RECUPERÁVEL A senha é usada apenas em memória e nunca gravada em disco ou no arquivo de estado. Se ela se perder antes de preparar o secundário, gere um novo certificado no primário (Menu 1 → etapa 10 → confirmar sobrescrita do PFX).
ℹ VALIDADE E RENOVAÇÃO O certificado expira em 5 anos. O checklist e o dashboard alertam quando faltarem menos de 90 dias. Para renovar: gere um novo no primário, reimporte nos demais hosts e atualize o thumbprint em Set-VMReplicationServer/Set-VMReplication (o próprio Menu 1 refaz isso ao detectar certificado inválido).

Opção 13 — renovar o certificado antes de expirar

O certificado do host vale 5 anos. Renovar à mão é arriscado porque o thumbprint fica gravado em dois lugares: na configuração do servidor Replica e na configuração de cada VM replicada. Esquecer as VMs deixa a replicação apontando para um certificado que não existe mais.

A regra que comanda a ordem é uma só:

A CA raiz nova precisa estar confiável em TODOS os hosts antes de qualquer host passar a apresentar o certificado novo. Isso porque a autenticação é TLS mútuo: o primário apresenta o certificado dele (EKU Client Authentication) e o replica valida contra a store Root; o replica apresenta o dele (EKU Server Authentication) e o primário valida do mesmo jeito.

ModoQuando é usadoO que fazer no PAROrdem
Reemitir só o certificado do host
(mesma CA raiz)		 Quando a chave da CA está disponível — HyperV_Replica_RootCA.pfx na pasta do script, ou a CA em LocalMachine\My. Importar apenas o novo .pfx. O par já confia na raiz, que não mudou. Livre — cada host pode ser renovado quando der, sem janela de risco.
Cadeia nova completa
(CA raiz + host)		 Quando a chave da CA não existe (cadeias criadas antes da v1.1.0) ou por escolha do operador. Importar .cer e .pfx, e aplicar antes de o primário aplicar. Obrigatória — ver os 4 passos abaixo.

Ordem no modo cadeia nova:

  1. No primário: opção 13 → GERAR. Gera os arquivos e não aplica nada — o certificado antigo continua ativo.
  2. Copiar a pasta do script (com o .cer e o .pfx novos) para o par.
  3. No par: opção 13 → IMPORTAR e aplicar. Instala a raiz nova e passa a confiar nela.
  4. Volta no primário: opção 13 → APLICAR. Antes de trocar, o script roda Test-VMReplicationConnection com o thumbprint novo; se o par ainda não estiver pronto, ele aborta sem alterar nada.

O diagnóstico que abre a opção 13 mostra o certificado do estado, o que o servidor Replica usa e o thumbprint de cada VM — divergência entre eles em amarelo. Os arquivos substituídos são preservados como *.anterior_<data>, e o certificado antigo só é removido se você pedir, depois de confirmar a saúde da replicação nos dois hosts.

07 Os três tipos de failover

Teste de failover — valide sem medo

Impacto na produção: nenhum. Quando usar: validação periódica do plano de DR (recomendado ao menos 1x por trimestre) e na entrega do projeto.

  1. No replica: Menu 2 → opção 4 — cria <VM> - Test desconectada da rede.
  2. Opcionalmente conecte-a a um switch isolado e ligue-a para validar o boot e os serviços.
  3. Encerre com a opção 5 — a VM de teste é apagada, nada persiste.

Failover planejado — migração sem perda de dados

Impacto: indisponibilidade controlada durante a janela. Quando usar: manutenção do host primário, migração de site, teste de DR "de verdade".

  1. PRIMÁRIO Menu 2 → opção 6: o script desliga a VM e replica as pendências (Start-VMFailover -Prepare).
  2. REPLICA a mesma opção 6 no outro servidor: failover, reversão da direção da replicação e inicialização da VM.
  3. A replicação continua funcionando — agora no sentido inverso. Para voltar, repita o processo.

Failover não planejado — o primário caiu

Impacto: possível perda das alterações desde a última replicação (até o intervalo configurado). Quando usar: somente com o primário indisponível.

  1. REPLICA Menu 2 → opção 7: escolha o ponto de recuperação (o mais recente ou um anterior), ligue a VM e valide.
  2. Só então complete o failover — completar remove os pontos de recuperação (sem volta a estados anteriores).
  3. Quando o primário voltar, siga o roteiro de reversão que o script imprime (-AsReplica no antigo primário → -Reverse → replicação inicial → failover planejado de volta).
✖ NUNCA LIGUE A MESMA VM NOS DOIS HOSTS Após um failover não planejado, se o primário original voltar com a VM antiga em execução, haverá conflito de IP/identidade (split-brain). Antes de religar o host recuperado, garanta que a VM antiga esteja desligada e marque-a como replica (Set-VMReplication -AsReplica).

09 Arquivos gerados pelo script

Tudo fica na própria pasta do script — por isso "copiar a pasta" é o mecanismo de transporte entre servidores.

🗂️
Estado_Replica_<HOSTNAME>.json

Progresso da implantação deste host (papel, ambiente, topologia, thumbprint, etapas concluídas, reboot pendente). Um arquivo por servidor — copiar a pasta não contamina o estado do outro host. A senha do PFX nunca é gravada aqui.

🔐
HyperV_Replica_Cert.pfx

Certificado do host com chave privada, protegido pela senha definida no primário. Necessário para preparar o secundário/estendido em HTTPS. Trate como material sensível.

📜
HyperV_Replica_RootCA.cer

CA raiz (parte pública, sem chave privada) — instalada em Autoridades de Certificação Raiz Confiáveis em todos os hosts. Sem ela o certificado do host não encadeia e a replicação é recusada.

🔑
HyperV_Replica_RootCA.pfx

Chave privada da CA raiz, protegida pela mesma senha. É o que permite renovar o certificado do host (opção 13) mantendo a raiz — sem este arquivo a CA não pode mais assinar nada e toda renovação exige cadeia nova nos dois hosts. Ele autoriza a emissão de certificados confiáveis pela topologia: guarde com o cuidado de uma senha de administrador e não o distribua junto com o secundário se não for renovar de lá.

🗄️
*.anterior_AAAAMMDD_HHMMSS

Versões substituídas pela renovação (opção 13). Ficam para trás como caminho de volta — apague só depois que a replicação estiver saudável nos dois hosts.

📊
Dashboard_Replica_AAAAMMDD_HHMMSS.html · Replica_Monitor_AAAAMMDD_HHMMSS.csv

Relatórios do Menu 3, com carimbo de data/hora — histórico natural das coletas.

🧾
Logs\Replica_<Operação>_AAAAMMDD_HHMMSS.log

Transcript completo das operações que alteram o ambiente (preparação, habilitar replicação, failovers) — evidência de campo para a documentação do projeto.

10 Solução de problemas

SintomaCausa provávelAção
Checklist: porta 443/80 inalcançável no par Firewall intermediário, par ainda não preparado, ou regra listener desabilitada no destino Conclua o Menu 1 no outro servidor; confira firewalls de rede entre os sites; a regra Hyper-V Replica ... Listener (TCP-In) deve estar habilitada no host que recebe.
Erro de autenticação ao habilitar a replicação (HTTPS) SAN do certificado não contém o FQDN usado, CA raiz ausente da raiz confiável, ou revogação habilitada Use exatamente o FQDN cadastrado na topologia; rode o checklist (Menu 3 → 6) nos dois hosts — ele valida cadeia, SAN, raiz e o valor DisableCertRevocationCheck.
0x80092007 — "O certificado especificado é autoassinado" Certificado com emissor = requerente (é a própria raiz) Regenere a cadeia no primário (Menu 1 → etapa 10): o script cria uma CA raiz e emite o certificado do host a partir dela. Confira no MMC que Emitido por mostra Hyper-V Replica Root CA, e não o FQDN do host.
0x800B0109 — "a cadeia terminou em um certificado raiz que não é confiável" A CA raiz (Hyper-V Replica Root CA) não está em Autoridades de Certificação Raiz Confiáveis da máquina local. O certificado do host está correto — falta apenas a raiz que o assinou. Reinstale a raiz a partir do .cer da pasta do script e repita a etapa: Import-Certificate -FilePath .\HyperV_Replica_RootCA.cer -CertStoreLocation Cert:\LocalMachine\Root. A partir da v1.0.1 a etapa 10 detecta e reinstala isso sozinha, e o checklist (Menu 3 → 6) traz o item "CA raiz em Autoridades Raiz Confiáveis".
FQDN do par não resolve (workgroup) Entrada ausente no arquivo hosts ou sufixo DNS não aplicado Reexecute o Menu 1 (etapa 7 é idempotente) ou confira C:\Windows\System32\drivers\etc\hosts — as entradas do script têm o marcador # HyperV-Replica.
Saúde Critical com replicação parada Destino sem espaço, rede indisponível por longo período, ou VM precisa de ressincronização Veja os eventos (Menu 3 → 3); libere espaço/rede; retome com Menu 2 → 9 (o Hyper-V solicita resynchronize quando necessário).
Saúde Warning após failover Direção da replicação não configurada (esperado após não planejado) Siga o roteiro de reversão impresso pelo script (seção 07).
Get-WindowsFeature não existe Script executado em Windows client O Hyper-V Replica só existe em Windows Server — use um host suportado.
